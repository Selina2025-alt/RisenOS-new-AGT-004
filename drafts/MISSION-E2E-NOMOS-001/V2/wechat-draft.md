# 多智能体越自主，企业越需要制度

设想这样一个企业任务。

一个智能体读取客户需求，一个智能体查询库存，一个智能体核对价格，还有一个智能体负责汇总结果。单看每个环节，都不难理解。可当它们开始互相委派、共享信息，并调用企业工具时，管理者很快会遇到一组更具体的问题：

谁可以读取哪些数据？谁有权提交最终结果？两个智能体判断不一致时，以谁为准？涉及价格、合同或资金的动作，在哪一步必须由人确认？如果最终结果出了问题，企业能不能还原当时发生了什么？

这些问题并不只关乎模型能力。它们直接关系到企业的职责、权限和经营责任。

这也是我们判断企业多智能体协同是否真正可用时，不能绕开的一层。

## 能力扩张：治理压力随之上升

过去，企业讨论智能体，注意力往往集中在模型能否理解任务、调用工具和完成结果。等到多个智能体进入同一项业务，问题会发生变化。

此时，企业面对的不再只是某个智能体回答得准不准。身份如何确认、权限如何授予、任务如何委派、过程如何审计，开始成为系统级问题。

2026年，NIST启动AI Agent Standards Initiative，并发布智能体身份与授权概念文件，把智能体身份、委托关系、授权范围、安全互操作和审计列为重点议题。[1][2]

OWASP针对多智能体系统的威胁建模研究，则将共享记忆、智能体通信、任务委派和级联失败列为需要单独处理的风险。[3] Google关于安全智能体的研究也强调，应当明确人类控制者，限制智能体的能力与权限，并让其行动保持可观察。[4]

这些公开资料没有为任何一家企业产品背书。它们共同说明的是一个行业问题：随着智能体从单点辅助走向相互协作，企业必须同时建设治理能力。

智能体可以越来越聪明，责任却不能越来越模糊。

## 协同难题：单体约束不够用

多智能体带来的第一个问题是准确性。

在单体场景中，企业主要检查输入和输出。进入多智能体环境后，一个智能体的输出可能成为另一个智能体的输入，工具返回的内容也可能继续影响后续判断。

AgentDojo的研究表明，外部工具结果和第三方内容可能通过间接提示注入影响智能体行为。[5] 这意味着，智能体之间传递的信息需要保留来源和验证状态。来自网页、工具或其他智能体的内容，不能因为进入了协作链，就自动变成可信指令。

第二个问题是稳定性。

一个智能体判断错误，影响可能停留在单个任务中。多个智能体互相调用后，错误可能沿着协作关系继续传递。任务反复转交、判断循环、局部失败无人接管，都会让一个看似简单的业务任务陷入停滞。

Microsoft Research在Magentic-One中采用调度者、任务账本、进度账本、停滞计数和最大尝试次数，正是为了让多智能体任务具备可观察的进度和明确的停止条件。[6]

第三个问题是复杂度。

当智能体数量增加，企业需要管理的已不只是任务顺序，还包括角色、数据、工具、权限、例外处理和人工责任。A2A协议将能力声明、任务生命周期、认证授权、状态追踪和人工介入纳入协议设计；MCP授权规范则强调资源级授权和最小权限。[7][8]

协议可以帮助智能体连接起来，但企业仍需要决定：谁可以连接、可以做什么、出了问题由谁接管。

## 研发演进：从编排走向制度

Nomos的研发起点，来自企业真实多智能体协同中的准确性、稳定性和复杂度问题。

这条研发路径并非一步完成。

早期阶段更多依赖固定编排。它的好处是任务顺序清楚，结果相对容易预期。不过，真实企业任务经常包含信息缺失、临时变化和例外情况，完全固定的执行路径很难覆盖全部现场。

随后，智能体开始获得更大的自主调度空间。它们可以根据任务状态选择工具、调整步骤，或者请求其他智能体参与。适应性提高了，新的问题也随之出现：谁能调整任务，调整到什么程度，触碰哪些数据时需要审批，出现分歧后如何处理？

所以，下一步需要解决的并不是把智能体重新锁回固定路径，而是为自主性建立可以执行的边界。

我们把这一步概括为“制度约束下的自主协同”。

制度需要说明角色和职责，也要定义权限、交接关系、人工确认点和例外处理。边界明确之后，智能体仍然可以根据现场信息作出判断。在这样的制度设计中，触及授权边界的动作需要暂停，并进入企业预先设定的确认或人工接管机制。具体能覆盖哪些动作，仍取决于实际制度配置、工具权限和接入环境。

这种设计追求的并非绝对控制。它要解决的是企业最关心的现实问题：智能体可以参与经营，但企业仍然掌握最终决策权，并且能够对过程负责。

## 产品落位：Nomos在何处

在艾氪智能的产品组合中，Nomos被定位为智能体团队产品线中的制度智能体。

这个定位回答的是“Nomos承担什么角色”。

从技术架构看，Nomos的底层制度协同机制位于JovaAI OS内部。它不是五级架构之外新增的第六层。这个表述回答的是“制度协同机制运行在哪里”。

两者属于不同维度，不能混为新的产品层级。

Nomos关注的，是智能体团队中的制度、角色与协同边界。产业知识和具体业务判断，仍由相应的产业能力、专业智能体以及企业责任人承担。制度智能体要解决的问题，是如何为这些判断提供企业可以设定、检查和追溯的协同规则。

这里还需要明确产品证据边界。

当前已激活知识支持Nomos的产品定位、研发起点和演进路径；涉及具体产品能力时，仍只按当前已演示范围表述。本文不据此宣称Nomos已经具备大规模生产稳定性，也不引用尚未授权的客户案例和量化效果。外部标准与研究只用于说明行业治理问题，不能转化为Nomos获得第三方验证的证明。

对企业来说，这个边界很重要。可信的企业AI内容，应当让管理者知道产品已经验证了什么，也知道哪些部分仍需结合实际环境继续验证。

## 行动判断：先回答四个问题

企业准备引入多智能体时，可以先回答四个问题。

第一，角色是否明确？

每个智能体承担什么职责，谁负责汇总，谁拥有最终决定权，需要在运行前说清楚。智能体名称和能力说明不能代替责任定义。

第二，权限是否具体？

智能体可以读取哪些数据，可以调用哪些工具，可以执行到哪一步，应当落到具体资源和动作。涉及合同、资金、客户数据及其他高风险操作时，要保留人工确认。

第三，异常能否停止？

智能体判断冲突、任务反复循环、证据不足或者执行超出边界时，系统能否暂停？谁来接管？可以重试几次？这些条件需要成为运行机制的一部分。

第四，过程是否可追溯？

企业需要保留来源、版本、任务状态、审核决定和操作记录。只有能够还原过程，管理者才有条件判断错误发生在哪里，以及下一次应该修改什么。

NIST的生成式AI风险管理框架同样强调角色责任、来源记录、人类监督、版本和事件留存。[9] 欧盟《人工智能法》第14条对高风险AI提出人类监督、干预和停止要求，但这一要求不能被扩大解释为适用于所有智能体场景。[10]

制度的价值，最终要落到这些具体问题上。

艾氪智能专注于企业AI与产业AI，并持续建设产业级Agentic OS和产业级多智能体协同操作系统。我们把Nomos放进这套体系，是因为企业真正需要的，不只是更多能完成任务的智能体，还需要一支职责清楚、权限明确、过程可查、关键决定仍由企业掌握的智能体团队。

如果一家企业已经开始部署两个以上的智能体，可以先不急着继续增加数量。先把角色、权限、人工确认和追溯机制画出来。

这张制度图能不能说清楚，往往比“还有多少智能体可以接入”更能判断企业AI是否准备好了。
